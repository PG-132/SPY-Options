## Problem

The scenario engine answers one what-if per terminal run. You write a position CSV, run `python app.py scenario`, and read a fixed-width report. Anything the report leaves out is in `grid.csv`, one row per leg per point per IV response. Changing a leg, the shift or the horizon means another edit and another run.

The report shows Greeks only at the start ("Greeks now, at fixed IV"). How they change across spot and dates is only in `grid.csv`. For the short Nov-20 750 straddle run with `--sessions 5` on `2026-11-10_1540`, that is 4 dates x 13 spots x 3 responses = 156 points, each with two legs and a total: 468 rows (arithmetic from the grid's rules, not a count of the file).

What the owner wants from the page (**Decided**: the owner's stated wants, relayed on 2026-11-13 and given directly on 2026-11-19; how each one is shown below is **Proposed**):

- Enter a position: option legs, plus SPY-share or NES hedges.
- See P&L and Greeks across spot moves and dates. Each point shows three P&Ls, under `none`, `moderate` and `large`, with the lowest and highest case named.
- See how the Greeks change with x movement in y time; the owner called this the main thing. On 2026-11-19 the owner settled what it means: "the % move across y sessions showing how the position evolved over y sessions".
- Keep the horizon (sessions after the snapshot) and each leg's days to expiry visible as separate inputs (IV response record, section 5, Decided 2026-11-11).
- Show the engine's flags.
- Show each snapshot's `run.json` warnings beside the grid. The engine does not repeat them.
- Leave room for typing an IV directly later: "IV will be 25% on Friday" (IV response record section 8; next action 2 in [../status.md](../status.md)).
- From 2026-11-19, in the owner's words: "dynamic interactivity with zooms, hovers, moving a 3d surface around, seeing how that surface evolves over snaps and comparing that to the integrated view"; "dependencies are fine".
- From 2026-11-20: each view in its own bordered window, which can be moved around and made bigger or smaller, "compartmentalizing these as we add them", in the dark theme. - Later on 2026-11-20 the owner stepped back from the detail views: "lets start minimally first", with general views before narrower ones. The distribution's shape stays as a later reference. ## Intended behavior

All **Proposed** (agent) unless marked otherwise.

### 1. What it is

A Dash app with Plotly charts, on the owner's machine, started from `app.py`:

    python app.py ui [snapshot] [--port N] [--no-browser]

- **Why Dash.** The owner asked for zoom, hover and a 3D surface that can be turned, and said dependencies are fine (**Decided**, owner 2026-11-19). Plotly draws all of that. Dash is Plotly's own app framework. Its callbacks are plain Python functions, so one chart can drive another: hovering a session on one chart can highlight it on the others. The choice of Dash over Streamlit is the agent's (**Proposed**). Streamlit would draw the same Plotly charts, but it reruns the whole script on every change, and its charts drive one another less directly.
- **Two modules:**
  - `screener/ui.py` is the view. Everything the page shows is built there as plain Python data, from the engine and the pipeline's files. It uses only the standard library and is tested without Dash. It also holds `cmd_ui()`.
  - `screener/ui_app.py` holds the Dash layout, the callbacks and the Plotly figures, built only from what `ui.py` returns. It is the one file that imports Dash or Plotly, in the way Webull is only in `collect.py` and Yahoo only in `prices.py` (AGENTS.md Conventions).
- **Without Dash.** `app.py` imports `ui_app` only when `ui` is run, so every other command works on a machine without Dash installed. If Dash is missing, `ui` says to run `pip install -r requirements.txt` and stops.
- **Running.** The server serves on 127.0.0.1 only, at port 8050 (Dash's default) unless `--port` is given, and prints its address. It opens the default browser unless `--no-browser` is given, and runs until Ctrl+C. Dash's debug mode stays off: its in-browser debugger can run code. It is not part of `daily`.

### 2. What a launch shows, and what changes from one launch to the next

The owner asked (2026-11-19) what is on screen when the page is first launched, and what changes each time.

**What `python app.py ui` does:**

1. It checks that Dash is installed.
2. It lists the snapshots carried through `surface` (`scenario.ready()`).
3. It loads one snapshot, read-only: the one named on the command line, or else the newest. "Load" means `scenario.load`, the same reading the CLI does: the raw chain, vol.py's IVs and forwards, the fit and the term structure. It is hashed either side of the read, as `run` does. If no snapshot is ready, it loads nothing and the page shows the empty state.
4. It starts the server, prints the address and opens the browser.

Nothing is priced and nothing is written at launch.

**What the page shows at launch:**

- **At the top:** "A what-if under the rules in scenario.py, not a forecast." Then the snapshot picker, set to that snapshot, with its start time (ET) and SPY at the start.
- **Beside it:** that snapshot's `run.json` warnings and the expiries `term.py` dropped (4.1).
- **The position editor:**
  - one blank row;
  - the list of saved position files in `positions/`, to load one;
  - the expiries and strikes it offers, which are that snapshot's.
- **The inputs at their defaults:**
  - move 0%;
  - horizon 5 sessions (a display choice, not a measurement);
  - IV shift 0;
  - no extra grid dates.
- **No results.** There is no sweep, grid or chart. One line says: "Enter at least one leg, or load a position, and press Price."
- **The chain view (4.6):** the IV surface and the variance strip of that snapshot, drawn straight away, since they need no position.

**What changes from one launch to the next:**

- **The snapshot it opens on.** It is always the newest ready at that moment. After `daily` adds one, the next launch opens there. Reloading the browser page picks up a snapshot added while the server runs, with no restart.
- **The numbers for a saved position.** A position file loaded on a newer snapshot is priced on that snapshot's spot, IVs and term structure, so its numbers differ from last time. Its `inputs` fingerprint differs too, which shows that they were priced from other data.
- **Nothing else.** No legs, inputs, results, camera angles or chosen snapshots are remembered from one launch to the next (**Decided**, owner 2026-11-19: "right now it shouldn't remember anything"). What lasts is only what was saved on purpose: position files in `positions/` and results in `data/scenario/`.
- **What never changes between launches:** the engine's rules and rates, unless `scenario.py` itself is edited.

### 3. One door to each source

`ui.py` calls the engine's library functions for every what-if, and nothing else that prices:

- `scenario.ready()`, new: the snapshots carried through `surface`, newest last. It is `latest()`'s rule; `latest()` becomes its last item, and nothing else about `latest()` changes. The page needs the list, and `latest()` calls `sys.exit` when there is none.
- `load(snapshot)`, hashed with `snapshot_hash` either side, as `run` does:
  - a snapshot whose files changed during the read is refused;
  - the loaded snapshot is kept, keyed by its hash, so a re-run of `iv` or `surface` is picked up at the next Price.
- `build_legs(ctx, rows)`, given the rows exactly as a position file gives them (strings). The strict reading of every number, and every refusal, are then the CLI's, in the CLI's words.
- `grid(ctx, legs, shift, position, sessions)` for the grid.
- `point(ctx, date, spot, shift, case)` and `price_point` for the sweep. The session's date comes from `sessions_after`.
- `grid_slope` per case, `extremes`, `leg_rows`, and `grid_spots` (for the size of one expected move).
- `FLAGS`, `CASES` and `CONFIG["response"]`, read for the text.
- `fingerprint`, for the `inputs` id.
- `run`, for "Save results" (section 6).
- `Refused`, which carries the reasons.

The chain view (4.6) reads the pipeline through the modules that own each piece, not re-parsed here:
- vol.py's IVs and bands come from `contracts.csv`;
- surface.py's fitted IVs, readable flags and fitted ranges come from `points.csv`, and its fit from `fits.csv`, evaluated only through `surface.smile_basis` (as `scenario.curve` does);
- the strip comes from `term.load`, `term.constant_maturity` and `context.decompose`;
- its session axis is the engine's clock, `ctx["clock"]` from `scenario.load`, so session s on the strip is session s of the sweep.

Only two kinds of arithmetic are the UI's own, both in `ui.py` and both tested:

1. **An input move becomes a spot.** A move of x% is `S x (1 + x/100)`. The spot is shown beside the input, with its size in expected moves: `ln(S'/S)` over the engine's move, the same measure as the grid's `moves`.
2. **A change from now.** An engine output at a point, minus the same output at the start.

Everything else is formatting and placing. The engine's docstring says why it should be so: so "there is one set of rules to argue with".

### 4. The page

**4.1 Snapshot and its warnings.**
- At the top: the picker, the start time, SPY at the start and, once something is priced, the `inputs` fingerprint.
- A column beside the grid and the sweep holds, in every state that has a snapshot:
  - the `warnings` from `run.json`, verbatim, headed "From the snapshot's run.json; the engine does not repeat these". On `2026-11-05_1633` there are three: market closed at 16:33, quotes 21 minutes old, and 10 band edges still carrying 1% delta (read from the file, 2026-11-13);
  - the expiries `term.py` dropped (`ctx["dropped"]`): legs on them keep a constant IV as the date moves (`no_term`; A-015).
- A snapshot with no `run.json`, or no warnings, says so in words.
- vol.py's own warnings are printed by `iv` and not saved, so there is nothing to show for them. The page says so.

**4.2 Position.** An editable leg table. Each row takes:
- the kind: option, shares or nes;
- the expiry, from the expiries vol.py read;
- the strike, from the strikes the chain lists on that expiry;
- the right;
- a signed quantity;
- the fill. It is required for NES; on an option it is recorded but not used, since entry is at mid.

Once priced, each leg shows what `leg_rows` gives:
- its IV and source;
- the band from `iv_bid` to `iv_ask`;
- bid and ask;
- entry at mid and at the far side;
- model minus mid;
- SPY shares per contract;
- flags.

The position shows its entry at mid and at the far side, and the NES conversion line when there is an NES leg. Beside the P&L: "entry is at mid; P&L runs from the model's start value, so model minus mid is beside it, not in it".

**4.3 The inputs.** Three boxes, kept apart (IV response record section 1; **Decided**, owner 2026-11-12):
- **Spot:** the move x, in percent (**Decided**, owner 2026-11-19), as a slider and a box. Beside it: the spot and its size in expected moves.
- **Horizon:** y, in whole sessions after the snapshot. It runs from 1 to the session of the position's last expiry; past that, every leg is settled. Also here: the grid's extra dates, a list of sessions, like `--sessions`.
- **IV:** the parallel shift in vol points, as `--shift`. One shift serves both the grid and the sweep. The response is not an input: all three cases are always shown. A typed IV comes here later (section 8).

Each leg's own days to expiry, and its IV under `none`, are shown in the sweep at every session, beside its expiry and apart from the horizon: the leg's own clock.

**4.4 The sweep: the position over y sessions at x%.** This is the main view (**Decided** as the view, owner 2026-11-19; its layout is **Proposed**).
- **The spot is held.** SPY is at x% from session 0 and stays there through session y. That is the grid row's own reading ("SPY moved there now and stayed"), so the change from one session to the next is time alone. The response to the move is the same at every session, by the horizon rule (**Decided**, owner 2026-11-12). A move spread across the sessions, or reached partway, is the engine's to model later (owner, 2026-11-19: "we'll still work on the scenario engine at a later point in time").
- **Rows:** session 0 (now), then every session from 1 to y. Each row has its date and close, and its sessions passed on the variance clock.
- **Columns:** P&L, delta, gamma, theta and vega, each under `none`, `moderate` and `large`. Each carries its range from the quote band (AC-19). Each Greek can show its change from now instead.
  - "Now" is the snapshot as it stands: its spot and time, with no shift and no response. P&L runs from it.
  - At session 0 and 0%, P&L reads 0 and the Greeks are contracts.csv's.
- **Lowest and highest case.** Named per row, from P&L (`extremes`). Nothing is named where the cases agree within $0.50.
- **Charts.** One for each quantity: P&L, delta, gamma, theta and vega against sessions.
  - Three lines, one per case, each with its range as a light band.
  - Hovering shows the value, its range, the date, and each leg's days to expiry and IV.
  - Hovering a session in one chart highlights it in the others.
  - Zoom and pan as Plotly gives them.
- **Per leg.** Clicking a session opens its legs: days to expiry, IV, `iv_response`, value, P&L, Greeks and flags under each case.
- **Grid slope.** Beside the delta now: the grid's slope at spot under each case, below and above (`grid_slope`), with the line that which one hedges SPY better is untested (SCEN-013; [../integrity.md](../integrity.md) item 5).
- **Units:** delta in shares, gamma in shares per $1, theta in $ per calendar day, vega in $ per vol point (pricing.py's units). Beside them, the engine's theta caveat: dates step on the session clock, so over a weekend the P&L moves by less than three days of theta.

**4.5 Grid: what `grid.csv` holds, absolutely.** The engine's grid at the shift and the extra dates given, and nothing else (**Decided**, owner 2026-11-19: "grid axes should show what grid.csv holds absolutely"):
- spot from 3 expected moves of the front expiry below spot to 3 above, in half moves;
- dates now, each expiry in the position, the session before the last expiry, and the extra dates.

The page's grid and the `grid.csv` that `scenario.run` writes for the same inputs hold the same numbers (AC-5).
- **Blocks.** One per date, headed with its sessions passed and every leg's days to expiry and IV under `none`.
- **Rows:** the engine's spots, in spot order: expected moves, percent and spot.
- **Quantity.** A chooser: P&L (the default), value, delta, gamma, theta or vega, with change from now for the Greeks.
- **Cells.** Each row has the `none`, `moderate` and `large` columns, each with its range. Each P&L row names its lowest and highest case.
- **Flags.** A point where a flag was raised carries a marker, with its codes on hover.
- **Chart.** Per date, the chosen quantity against spot: three lines with their bands, and hover and zoom.
- **Order.** No control on the page sorts or ranks anything by a figure.

**4.6 The chain view: the IV surface beside the variance strip.** A second tab. It needs no position, and is a measurement, not a what-if: every figure on it is vol.py's, surface.py's, term.py's or context.py's, read as section 3 says. The two views sit side by side and always show the same snapshot (**Decided**, owner 2026-11-19: "i want to see both views, the graph and the variance strip").

- **Windows.** The surface, the strip, and the snapshot's facts and warnings each sit in a bordered window. A window moves by its title bar, resizes from its lower-right corner, and comes to the front when clicked; its chart follows its size (**Decided**, owner 2026-11-20: "a bordered window that you can make bigger/smaller, move around").
  - The snapshot slider and the switches stay in a bar across the top, since they drive every window.
  - Each view added later gets a window of its own.
  - Where windows sit is not remembered from one launch to the next, like everything else (section 2).
  - **Built without a new package** (**Proposed**): a CSS resize corner, and a small script in `screener/assets/` that moves windows and changes nothing else. It reads and computes no figure.
  - **Considered and not used:** a grid-layout package for Dash, which would add a dependency for what about 30 lines of script do.

- **Stepping through snapshots.** A slider over every snapshot carried through `surface`, with previous and next buttons. A step redraws the surface, the integral and the strip together, from that snapshot's files (**Decided**, owner 2026-11-19). The snapshot is the page's one snapshot: stepping here also moves the position tab, whose results then go stale until the next Price. Nothing is animated; a step is a redraw.
- **Kept across steps.** The camera angle and zoom stay as you left them: the camera Plotly reports after each turn or zoom (`relayoutData`) is set on the next figure. `uirevision` alone did not keep it in the build (section 9). The axes stay fixed across the snapshots held, so that a change in level shows as a change rather than being rescaled away. An "auto" switch fits the axes to one snapshot instead.
- **The first view.** From the front: strike left to right, the nearest expiry in front, IV up (built 2026-11-19).
- **The page's colours.** A muted dark grey page (`#262624`) rather than white (**Decided**, owner 2026-11-20: "the white is just too bright for me"). On it go the reference palette's dark-mode steps: light text, the dark-mode orange for the points, light smiles, and the blue IV scale running dark for low IV to light for high. Dash's own controls are recoloured through its `--Dash-*` variables. Every colour is one constant at the top of `ui_app.py`.
- **Later, with comparing snapshots:** the snapshot before, drawn faintly on the integral and the strip, and as a wireframe on the surface (AC-29). A wireframe rather than a second see-through surface, because Plotly can draw overlapping see-through surfaces in the wrong order (section 9). It moved out of step 2 on 2026-11-20 to go with the comparison the owner wants, which is to be scoped with them.

**The surface (3D, can be turned, zoomed and hovered; **Decided** as wanted, owner 2026-11-19: "i really would like my 3d view"):**
- **Axes:**
  - strike;
  - expiry, placed at its sessions from the snapshot on the engine's clock and labelled with its date, so that it lines up with the strip;
  - IV, in percent.
- **Points.** Every IV vol.py read (`contracts.csv`, the out-of-the-money side), each with its band from `iv_bid` to `iv_ask` as a vertical error bar. Points surface.py left out of the fit (`readable` False in `points.csv`) are drawn hollow, with its `why_not` on hover. They are hidden at first and shown from the legend: Plotly does not clip 3D points to fixed axes, and they hung outside the box. Across the 22 snapshots held on 2026-11-19, the 12,000 IVs the fit left out have a median of 24.9%, a 90th percentile of 64.9% and a maximum of 130.3%. The 24,952 it used have 18.1%, 34.7% and 68.9%, so the fixed axes run from 8.3% to 69.3% IV and from strike 475 to 855 (built 2026-11-19).
- **Lines.** Each expiry's fitted smile, through `points.csv`'s `fitted_iv`, drawn only between the strikes it was fitted on. That is the standing rule; the fitted range is the one the engine uses.
- **The surface itself.** A solid surface, coloured by IV.
  - **What it is.** surface.py's fit, evaluated by `surface.smile_basis` at one strike grid shared by every expiry. It is evaluated only inside each expiry's fitted range and left blank outside it.
  - **Why a grid.** Any 3D library draws a surface over a grid or a mesh, and the chain is neither: each expiry reads its own strikes. So the fit supplies the grid, as it does for the engine's `fit_iv`.
  - **Between expiries.** The faces between two expiries are drawn by the renderer, not measured, and the page says so. Hover on the surface is labelled "fit"; hover on a point gives the measurement.
  - **Contours.** Lines of equal IV on the surface, every 2 vol points, and their projection onto the box's IV wall farthest from the eye: the floor seen from above, the ceiling seen from below (corrected 2026-11-20; first written as "the floor" only). They can be switched off.
  - **Slices.** Hovering or clicking an expiry, on the surface or the strip, highlights its smile (built with step 3, where a click holds the highlight). Clicking a strike to highlight it across every expiry, its term structure, waits for later (question 24).
- **Hover on a point:** expiry, strike, right, IV and its band, delta, the fitted IV and residual, and readable or why not.

**The strip, the integrated view (2D, two panels sharing the session axis):**
- **The integral (upper panel).**
  - **Variance-swap total.** The total variance from the snapshot to each expiry: `term.load`'s `total_var`, with `total_var_error` as its error bar, starting from zero at the snapshot (`context.with_spot`). The points are joined by straight lines in sessions, which is how `term.constant_maturity` reads between them.
  - **ATM total.** Beside it, the ATM total variance to each expiry, `atm² x T`, with its error. `term.load` does not carry that yet, so it gains `atm_total_var` and `atm_total_var_error`, worked out in the same place and the same way as `total_var` (a small `term.py` change; no saved column changes). The gap between the two lines is the variance the wings add.
  - **Hover points.** The panel has a hover point at every whole session, from `term.constant_maturity`, and at every expiry.
- **The strip (lower panel).** Each window between adjacent expiries, from `context.decompose`, so the front window from the snapshot (the rest of today) is included.
  - **Steps.** Each window is drawn as a step across its sessions at its `forward_vol`, with `forward_vol_error` as an error bar at its middle. Its `forward_var` is in the hover.
  - **Not a `forward_var` switch,** as first written (corrected 2026-11-20). term.py carries an error for forward vol but not for forward variance, so a variance axis would be the one figure on the page without an error bar.
  - **Individual days.** A one-session window is labelled with its date (`session_priced`).
  - **Marked:**
    - a negative window;
    - one negative beyond its error bar (`arbitrage`);
    - a window widened by dropped expiries (`spans_dropped`, A-015);
    - every window's `edge_margin`, shown on hover with the line term.py's report gives it.
  - **Hover on a window:** its expiries, sessions, calendar days, 1pm closes, source, ATM IV and skew at its far end.
- **Highlight at a point in the integral** (**Decided** as wanted, owner 2026-11-19: "proper highlights at a point in the strip integral"). Hovering session s on either panel:
  - draws a vertical line through both panels;
  - reads the integral at s and names the window s falls in;
  - shades, faintly and at full height, the sessions from the snapshot to s, labelled "time included in the total": a selection aid marking included time, not an area equal to the integral, since the lower panel is forward vol and total variance adds forward variance times session length / 252 (question 22, settled by the agents);
  - outlines the window around s, in amber;
  - thickens the two expiries either side of s on the surface, in amber (the same colour marks the same window in both views).

  Hovering a smile, a point or the surface on the surface outlines its expiry on the strip. Every value shown in a highlight is one the view supplied (`term.constant_maturity` at whole sessions, the windows' own figures). The page reads between nothing. Built 2026-11-20 as AC-27 details it: one readout line above the strip, a click to hold, and no integral reading for an expiry outside the term structure.

**4.7 Flags and stated assumptions.**

- **Stated once, read from `CONFIG`**, so a change to the rates shows on the page without editing it:

**4.8 Detail views (Proposed, 2026-11-20; deferred the same day).** Kept as a later reference: the owner chose to start with general views (4.9). Each is a window of its own (4.6). None is built, and the order and choices wait on questions 10 to 14. Every figure would come from the pipeline, and the parts it does not measure yet are named.

- **Where a strike sits in the bell curve.** Each strike's distance from the forward in expected moves, ln(K/F) over the ATM vol times the square root of T, is already measured: vol.py saves it as `moves_from_forward` in `contracts.csv`. It remains with these deferred detail views, outside step 3 (question 24, accepted 2026-11-20).
- **The move.** Each expiry's priced move from its total variance: one standard deviation of the log move is the square root of the total, as a percentage and in dollars. It is drawn in two places:
  - as a cone on the surface's floor, the strikes one move either side of the forward at each expiry, so the strikes inside it can be seen;
  - as a readout per expiry.

  It needs a term.py function giving the move and its error (from `total_var_error`); nothing computes it yet. Not on the strip's axis: the strip shows the variance the move is the root of, and one axis means one unit.
- **The distribution, one expiry at a time.** The density of SPY at the chosen expiry that its total variance implies, drawn as a lognormal:
  - one curve from the variance swap rate and one from the ATM level; the wider one is the wings' variance;
  - the curve from the snapshot before, drawn faintly beside it, which shows it widening or shrinking;
  - the hovered strike marked on it at its distance, with the chance the curve gives of finishing beyond it;
  - SPY's actual move since the snapshot before, marked on that snapshot's curve in standard deviations: where the move landed against what was priced, as the ledger's settlement measures windows.

  All of it is what the chain prices, not a forecast of where SPY goes. The lognormal is symmetric in log terms, and the smile says the market is not: it prices a fatter left tail. The truer curve is the one the smile implies (the second derivative of call prices in strike, from surface.py's fit, inside its fitted range only). That is a new measurement, with its own error bars and an unknown mass past the fitted range, so it would be a change of its own, measured before it is drawn.
- **The 25-delta and 10-delta points.** Each expiry's 25- and 10-delta put and call, marked on its smile on the surface. A skew window beside it would show each expiry's put and call minus ATM, against the snapshot before. vol.py measures these IVs (`at_delta`, interpolated by delta between two strikes) but saves no error band and not the strike, so vol.py would carry both first. That adds columns to `expiries.csv` and means re-running `iv`, which changes the fingerprint of saved scenario results. concepts.md's caution applies: skew shrinks with maturity as a matter of structure, so one expiry's skew falling over days is mostly ageing, not news.
- **Comparisons,** built on what `history.py` already measures across every snapshot: the four comparisons of concepts.md ("Three ways to compare two days"): fixed expiry, constant maturity, per session, and fixed strike across a move. The window-by-window table the agent read out on 2026-11-20 (Friday 11-13 against Monday 11-16) is the per-session view.

**4.9 Implied against realized, by term structure (Proposed, 2026-11-20).** The owner's next general view: what the snapshots priced against what SPY then did, kept apart by where in the term structure it was priced. Each grain is a window of its own. All of them stand on what the pipeline already records.

- **What "term structure" means in the screener today** (**Observed**, from the code):
  - **The strip's windows.** term.py splits each chain into windows between adjacent expiries, the front one from the snapshot (context.py). Each window has a start, its sessions ahead, a length in sessions, and a forward vol with an error.
  - **Constant maturity.** term.py reads the rate 5, 10 and 15 sessions out, so one horizon can be followed from day to day.
  - **The 30-day rate.** context.py reads it against VIX; vrp.py logs it.
  - **One-session windows.** These price a single date and can be followed as that date approaches (concepts.md, "Three ways to compare two days").
- **The record already exists.** `ledger.py` keeps every window of every snapshot and settles each one against SPY's closes over exactly its sessions once they close. Each row carries its priced forward vol, its realized vol, how many returns it held, and where in the chain it sat. `ledger.pooled` already compares realized with priced the bias-free way, pooled in variance (a one-session |return| alone averages 0.80 of the true sigma). On 2026-11-20 the ledger held 245 rows from 22 snapshots, 141 of them settled.
- **The three grains, as the owner put them:**
  - **Month.** `vrp.py`'s monthly claims: VIX against SPY's realized over the next month, non-overlapping, since 1993 (405 months in `data/vrp/vrp_monthly.csv`). The screener's own 30-day rate (`our_implied.csv`) goes beside it. The file is as fresh as the last `python app.py vrp`, which is not part of `daily`; its last run left October open at 13 sessions.
  - **Term structure.** The ledger's settled windows, grouped by where they start. Read-only on 2026-11-20 (one snapshot a day, full-width bands, `ledger.pooled`; 95 windows over only 24 distinct dates, 10-15 to 11-18), realized over priced was:
    - 1.08 for the window from the snapshot (16 windows);
    - 1.50 at 1 to 4 sessions ahead (47);
    - 1.25 at 5 to 9 (28);
    - 1.46 at 10 and beyond (4).

    These are illustrations, not results: there are no error bars, the dates overlap, and the -4.4% day of 11-05 sits inside them.
  - **Day.** One date at a time: each snapshot's forward vol for it as it approached (the ledger's pivot), against the return it realized.
- **The owner's answers (2026-11-20; questions 15 to 19).**
  - Three windows: the day, the term structure, then the month.
  - One snapshot a day, with error bars.
  - Grouped by where windows start, with one-session and multi-session windows kept apart. A strike moving in or out of a window must not make an artificial value.
  - An event calendar comes first, for context. The order is step 3's highlights, then the calendar, then this table.
- **Time passing (the owner's concern in question 15, resolved 2026-11-20).** A window is a rate per session: term.forward_windows divides the difference of two totals by the sessions between them, and the ledger sets it against realized over the same sessions. So it does not shrink as its expiries come nearer. What shrinks is the total to a fixed expiry, the integral's upper panel, which loses a session's variance each day unless the market reprices. Read-only on the last ten snapshots, the total to 2026-12-18 still rose from 0.00327 (11-11) to 0.00693 (11-20): repricing outweighed the decay. The window from the snapshot also carries the rest of the snapshot's own session (`context.with_spot`), so the time of day a snapshot is taken leaves no sawtooth.
- **Strikes moving in and out (the agent's reading of question 15; its safeguards agreed 2026-11-20).** Each window's priced vol is the difference of two variance swap totals, and each total is an integral over the strikes its expiry carried at that snapshot. That strike set changes every session, so a window's number can move without anything being repriced. Measured read-only on the 22 snapshots held (2026-11-20), it shows up three ways:
  - **The band.** That is how far out the chain was collected. 09-24, 10-12 and 10-13 were 6/3, 10-15 was 20/10, and every snapshot since 10-20 is 12/6. A narrower band understates the rate. The ledger keeps the band on every row and `converged` leaves 6/3 out, but it still pools 20/10 with 12/6.
  - **The edge.** An expiry whose strikes run out before its integral dies is dropped from the strip (`max_vs_edge_cost`), and its two windows become one wider window (`spans_dropped`). Each snapshot had 0 to 12 expiries over the limit (12 of 15 on 11-05), leaving 0 to 2 widened windows. An expiry near the limit can be in one day and out the next, so the same dates sit in one-session windows one day and in a widened window the next.
    - Found 2026-11-20 while scoping step 3: the window from the snapshot is never marked widened, even when it stands in for dropped expiries. That happened on 3 of the 22 snapshots, among them `2026-11-05_1633`, whose front window covers five dropped expiries ([../specs/term.md](../specs/term.md) Gaps; question 20). So the widened windows counted above miss those three.
  - **The count inside a full band.** The 2026-12-18 expiry was integrated over 222, 229, 244, 252, 238 and 255 strikes on its last six snapshots. The outermost pair was worth 0.007 to 0.015 vol points, a lower bound on what the edge leaves out.

  The safeguards for the view (**Decided**, owner 2026-11-20: agrees with Claude's suggestions except shading; the precise reading of question 15 remains unstated):
  - each window is compared only with the realized over its own sessions, never with "the same group yesterday";
  - one band is pooled at a time (12/6 since 10-20), with any other shown apart;
  - a widened window stays in the multi-session group, matched by its interval. The day grain shows a gap for a date inside it, never a made-up one-session value;
  - every window carries its edge margin, so one near the limit is marked.
- **What the pipeline does not do yet:**
  - put an error bar on a pooled ratio;
  - count one observation per date rather than per row (many snapshots price the same date against the same realized return);
  - put an error on a month's realized;
  - tell event days from ordinary ones. The ledger's docstring says its rows mean little in aggregate until they are separated; there is no event calendar yet.

  Each of these goes into the module that owns it, with tests, before the page draws it.

### 5. States

- **Loading.**
  - At launch: the snapshot loads before the server starts, and the terminal says so.
  - On Price: the results area shows Dash's loading indicator, saying "pricing".
  - On a snapshot change: the indicator says "loading the snapshot", the slow part.
  - Moving the x or y slider updates the sweep while the slider moves.
- **Empty.**
  - No snapshot is ready. The page names the commands to run (`python app.py daily`, or `iv` then `surface`), and the server stays up.
  - A snapshot but no legs. The snapshot, its warnings and the editor are shown, with the line from section 2.
  - Hedge legs only. These are priced, and the date blocks say "no option legs", as the CLI does.
- **Error.**
  - A refusal. Every reason the engine gives is listed beside the editor, in its words. The inputs stay as typed. No numbers from earlier inputs stay on screen.
  - Data that changed while it was read. Refused, as `run` refuses it, with "run this again".
  - Anything unexpected. One line on the page ("the engine failed: type, message; nothing priced"), with the traceback in the terminal. The server goes on answering.
  - Dash not installed. The command says how to install it and stops.
- **Success:** sections 4.1 to 4.7.
- **Stale.**
  - Once the legs, the snapshot or the shift change after a Price, the results are greyed and marked "priced from other inputs" until Price is pressed again.
  - The x and y sliders never go stale, since they reprice as they move.
  - Every result shows the inputs it was priced from, and their `inputs` fingerprint. That is the one `scenario.run` stamps for the same position on the same data, so a screen can be matched to a saved `grid.csv`.

### 9. What Dash and Plotly cannot do here

Asked by the owner before the build (2026-11-19). The versions are those a `pip install --dry-run dash plotly` resolved on the owner's Python 3.14.3 the same day: Dash 4.5.0 and Plotly 7.1.0, with 21 supporting packages, among them Flask, Werkzeug and pydantic (**Observed**). Dash's changelog says 4.5.1 "is tested on 3.10 through 3.14". Plotly 7.0 and 7.1 list no change to 3D traces, error bars, hover or `uirevision` (**Sourced**: the `CHANGELOG.md` files of plotly/dash and plotly/plotly.py on GitHub, read 2026-11-19).

- **A surface needs a grid. That is the data's limit, not Plotly's.** Corrected 2026-11-19: this bullet first read as though another library would draw a truer surface. Any 3D library (Plotly, VTK, three.js) draws a surface over a grid or a triangulated mesh. The chain's expiries each read their own strikes, so the grid comes from surface.py's fit, and the measured points sit on it with their bands (4.6). Plotly draws that solid, coloured, with contours, turned, zoomed and hovered.
- **Where Plotly's 3D is weaker than a scientific 3D engine such as VTK:**
  - no planes to drag through the scene to slice or clip; slices are clicked or set by a slider instead;
  - overlapping see-through surfaces can draw in the wrong order, hence the earlier snapshot as a wireframe;
  - lighting can be adjusted but casts no shadows;
  - a 3D highlight is a redraw of a trace, not a style change.

  None of these is needed for what 4.6 describes.
- **Hover snaps to the points a chart carries.** It does not read between them. So the view supplies a point at every whole session and every expiry, and a highlight lands exactly on one of those. (Dash 4.5 can also report a hover anywhere on a chart; that is not needed.)
- **Each linked highlight is a round trip.** Hovering one chart and highlighting another goes to Python and back. Locally that is expected to be quick; the build times it. If it lags, the fix is a few lines of browser-side code that only switch which prepared highlight is shown, computing nothing.
- **No shaded bands in 3D.** Shaded areas and outlines exist on 2D charts only. On the surface, a highlight is a thicker line or a larger marker.
- **A redraw resets the camera unless told not to.** `uirevision` keeps the angle and zoom across snapshot steps. Dash 4.4.1 and 4.5.0 fixed partial updates undoing graph interactions, so nothing older than 4.5 is used.
- **The interactions are not tested automatically.** Hover, highlight and turning the surface would need browser tests (Selenium and a driver, more dependencies). The numbers behind every chart are tested offline; the interactions are checked by hand and recorded.
- **Static image export needs Kaleido.** Not planned: the chart's own camera button saves a PNG in the browser.
- **Found in the build, 2026-11-19 (Observed, Dash 4.5.1, Plotly 7.1.0, plotly.js 4.1.1):**
  - **A surface's hover label.** plotly.js shows "-" for a surface's `hovertemplate` fields from `text` or `customdata`, though both arrive as a full grid. It shows the grid through `hoverinfo="text"`. But plotly.py accepts a surface's `text` only as a flat list, turning each row into one string. So the label grid is set on the plain figure dict Dash is sent, past plotly.py's checks (`ui_app.surface_figure`).
  - **3D points past a fixed axis are not clipped.** They draw outside the box. Hence the left-out points start hidden (4.6).
  - **The camera on a step.** With `uirevision` set, a step to another snapshot reset the view in the browser. A synthetic drag also never registered as the user's own change, so `uirevision` could not be confirmed either way. The camera is now taken from `relayoutData` and set on each new figure, which works whichever way Plotly treats it.
- **Found in step 3, 2026-11-20 (Observed, same versions):**
  - **A surface cell's hover carries no customdata.** plotly.js leaves a surface's customdata out of its hover event, and Dash passes on only the cell's x, y, z and trace number (its pointNumber pair is dropped too). So a cell is matched to its expiry by its y, the expiry's own sessions, on the trace the page records as the surface.
  - **A highlight as a `Patch` keeps the camera.** Only the strip's shapes and the surface's first trace are sent; the layout is untouched, so the view the user turned to stays (checked after turning the camera, and after hovering on 11-05 and 11-19). Nothing needed carrying, unlike a step.
  - **The round trip is quick.** 5 to 17 ms per highlight against the local server, against 271 ms for a snapshot's first draw. No browser-side switching is needed.
  - **3D clicks only come from a real mouse.** plotly.js emits a 3D click from its render loop when a frame sees the button held over a picked point. The browser pane's clicks, and dispatched mouse events, never do, so a click on the surface was not made here. The page's response to it is tested offline.
  - **A readout that changes height moves the chart under the mouse.** The next point under it then fires its own hover, so the readout has a fixed height and scrolls.
  - **On a blue surface, a highlight needs a hue that differs in lightness too.** Light ink was lost among the light smiles, and aqua sank into the blue at the same lightness. Amber (palette slot 4) reads from every angle tried.

**Alternatives weighed for the 3D view** (asked by the owner on 2026-11-19, to avoid converting later). PyPI was read the same day for versions and wheels:
- **trame with PyVista (on VTK).** A scientific 3D engine: planes dragged through the scene, see-through surfaces drawn in the right order, full lighting. It installs on Python 3.14 (VTK 9.7.2 ships cp314 wheels; PyVista 0.49.2; trame 4.0.0).
  - Against it here: its 2D charting is not its strength. The strip, the sweep and the grid would come from a second library inside it, with two hover models to link.
  - It is also a large compiled install.
  - It is the one to move to if the 3D ever needs slicing planes or stacked see-through surfaces.
- **A JavaScript front end (three.js).** The most 3D control there is. But the page would become a JavaScript project, with its own build tools, tests and second language, for one person to maintain.
- **`dash-vtk`, VTK inside Dash.** Last released 2021 (0.0.9), so not relied on.
- **The agent's pick (Proposed): stay with Dash and Plotly.** The 3D in 4.6 is within what Plotly draws, the 2D is Plotly's strength, and one library makes the linked highlights direct.

**Keeping a later change cheap:**
- Every figure is built as plain data in `ui.py` and tested there, and only `ui_app.py` draws. Moving to another renderer would mean rewriting the drawing file, not the numbers or their tests.
- Dash also takes custom components, so a stronger 3D view could later replace the one chart inside the same page.
- The chain view's surface is built first, on real snapshots, and shown to the owner before anything else is built on Plotly (Tasks).
